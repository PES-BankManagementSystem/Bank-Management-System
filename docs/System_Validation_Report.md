isolated directory. Existing root `CMakeLists.txt` edits, the deleted
`db/.gitkeep`, and prior output were preserved. The initial validation used unchanged application source. TC-22 was then
retested at `00ffd7c` after adding accessible scrolling to dashboard/audit tables;

[Retest provenance](reports/system-validation/tc22-retest-2026-11-07/provenance.json). Windows GCC/MinGW 14.2 built the server using the environment flag
`-D_WIN32_WINNT=0x0A00` and existing pinned dependency sources. See
[build/test provenance](reports/system-validation/final-2026-11-07/build.json).

Every newly executed case had its own database initialized from the tested
revision's schema and seed and a new backend process. Browser core and responsive
runs also used separate fresh databases for each browser. Evidence records build
SHA, UTC timestamps, assertions, request statuses/timings, initial seed counts and
final database SHA-256. Database files, tokens, temporary passwords and server logs
are excluded from committed evidence. Screenshots contain fictitious demo data.

Declared fixtures: TC-05 adds a zero-minimum type; TC-07 adds a zero-balance
account; TC-08 sets ACC001 to INR 10,000; TC-09 configures the INR 25,000 limit and
inserts a prior-UTC-day withdrawal before server startup; TC-10 sets source and
destination to INR 10,000/5,000; TC-18 adds 12 dated deposits with consistent
running balances; TC-19/TC-20 each independently add 3,000 accounts (3,005 total).
The committed runners reproduce these adjustments.

TC-09 checks UTC date partitioning with a synthetic prior-day fixture, not an
observed real-time midnight rollover. TC-10 injects a credit-insert error after
debit and verifies rollback, rather than killing the process. TC-18 verifies the
CSV Blob generated by the actual download button; native OS save completion is
not claimed. Performance measurements use sequential requests, not concurrent
stress load. These qualifications apply to the PASS labels below.

**TC-15 was not rerun**, as requested. Its prior fresh-seed TLS result at
`b66f97c` is retained explicitly; it is not a new TLS result at the current SHA.
