# Deviations log

Every place where the implementation differs from the SRS v1.0, the SADS v1.0 or the Test Plan is listed here, with the reason. The log is reviewed at the end of each sprint (S-39).

| # | Affected document and section | Deviation | Reason | Story |
|---|---|---|---|---|
| 1 | SADS 3.3 (Error Handling, concurrency conflicts) | SQLite does not have row-level locking. Balance-changing operations take a database-wide write lock (`BEGIN IMMEDIATE`) instead, so concurrent writes run one at a time. | SQLite was chosen as the relational database ([ADR 001](decisions/001-tech-stack.md)). SRS Appendix D lists record-level locking as future work, and serialised writes give the same guarantee that no update is lost. | S-01 |
| 2 | SADS 2.4 / SEC-1 (authenticated operator identity) | The S-17 deposit route records seeded Bank Officer user ID `2` as the operator because authentication and session management are not implemented yet. The operator ID is server-side and cannot be supplied by the client. | This keeps the deposit's audit and transaction records complete until S-07 provides a verified session identity. The unauthenticated demo route must not be used in a production deployment. | S-17 (#44) — **resolved by S-10 (#40):** deposit, withdrawal, transfer and interest routes now require a signed-in session and record the real operator; the fixed demo operator IDs are gone. |
| 3 | SRS 4.2.3 (FR-3); SRS 3.4; SADS SEC-2; Test Plan TC-03/TC-04; Test Cases TC-03/TC-04 | S-11 creates a linked customer login with a generated 20-character temporary password, stores only its Argon2id hash, sets `must_change_password`, and returns the temporary password once in the 201 response for the Bank Officer to hand over. The browser keeps the bearer session in memory and shows the password only in the immediate success view. This is an explicit exception to SADS SEC-2's rule that plaintext credentials “shall never be logged, cached, or transmitted.” No email or SMS is used. This route is enabled only when the server binds to a loopback address or serves HTTPS (S-28); network deployment over plain HTTP remains unavailable. | S-11's backlog acceptance requires a customer login with initial credentials but does not specify delivery. The approved implementation choice permits one-time officer handoff as a scoped exception; SRS 3.4 also says Version 1.0 requires no email or messaging interfaces. Plain-HTTP listeners that are not loopback block one-time delivery; S-28 added the HTTPS option that lifts that block. SRS FR-3 §4.2.3 (page 11) specifies customer records and unique identifiers, but not login creation or credential delivery. The Test Plan (page 5) maps TC-04 to missing phone / FR-3; the separate Test Cases DOCX maps TC-04 to account opening / FR-4. S-11 follows the Test Plan's TC-04 meaning; resolve the test-document mismatch in a future documentation update. The S-11 prompt also requests email because the existing schema requires it; email is therefore accepted, validated and stored. Customer-code format (`CUS-` plus 8 random base32 characters), username = customer code, phone format, ASCII-only name characters, and DOB age limit are implementation assumptions because the source documents do not specify them. Schema version 2 adds customer codes, identification references, and the forced-change flag; `db/migrations/002_customer_credentials.sql` upgrades existing version 1 databases. A minimal in-memory bearer-session login/logout and first-login password-change endpoint were added because the existing auth routes were stubs; sessions expire after 30 minutes and are lost when the server restarts. Session enforcement was first applied to S-11 only; S-10 (#40) has since put every existing route behind session authentication and the role permission table. |

| 7 | SADS SEC-2 (credentials never transmitted); SRS FR-13 | `POST /staff` returns a generated 20-character initial password for the new Bank Officer once in the 201 response, stores only its Argon2id hash and sets `must_change_password`. Like customer registration (row 3), the route is refused on network-accessible plain-HTTP listeners; it works over HTTPS (S-28). Officer usernames are 3-32 lower-case letters, digits, `.`, `_` or `-`; the `users` table has no name column, so officers are identified by username only. Deactivation sets `status = 'inactive'`; users are never deleted, so the officer's ID stays on past transactions and audit entries. | S-24 asks for "initial credentials" without saying how they are delivered; this follows the approved S-11 one-time handoff pattern. Usernames and the no-name decision avoid a schema change. | S-24 (#56) |
| 8 | Test Plan §14.1/§14.2 TC-03 and TC-04; Test Cases DOCX TC-03 and TC-04 | The FR-3 test mapping conflicts: the Test Plan maps both TC-03 and TC-04 to FR-3 and defines TC-04 as a missing-phone customer-record test; the DOCX defines TC-04 as FR-4 account opening and maps FR-3 only to TC-03. | 9 | SRS §4.2.3; SADS SEC-1/SEC-3 and API endpoint table | Customer self-service is read-only and limited to the caller's own record; requesting another customer ID returns 404, while customer update requests return 403. Customer IDs use `customer_code`; numeric internal IDs are not accepted and return 404. Immutable customer/login identifiers and `createdAt` are rejected if supplied to the update endpoint. A `GET /customers/me` endpoint is added so a customer can load their profile without exposing another customer's search endpoint. Customer personal-data endpoints are disabled on network-accessible plain HTTP listeners. | The 404 choice follows S-12's privacy acceptance criterion. The SRS limits customers to their own profile; the SADS endpoint table lists officer/admin roles for customer-record GET/PUT, and SEC-3 requires HTTPS for network deployment. The login response does not provide a customer ID. | S-12 (#42) |
| 10 | SRS §4.2.3; SADS customer/account model; `db/schema.sql` | At S-12, summary `status` was derived from the linked user's status (or `active` when no login existed); S-13 supersedes this with an independent customer lifecycle status while login status remains on `users`. | 11 | SRS §4.2.3 FR-3; SRS §5.5; SADS customer API table; Test Plan §14.1/§14.2; Test Cases DOCX | The S-13 story restricts customer deactivation to Administrators, although FR-3 and the SADS `PUT /customers/{id}` row list Bank Officers and Administrators. No customer reactivation route is added because neither SRS nor SADS specifies one. Inactive login attempts use the generic `Invalid username or password.` message (locked users retain the documented lockout message). Repeated deactivation is idempotent and adds no duplicate audit row; existing bearer tokens are denied by the existing per-request user-status check. Account opening does not exist yet, so the tested `require_active_customer` guard must be called by the future account-opening story. Staff may continue editing inactive customer records because the SRS is silent on this case. The Test Plan maps TC-04 to a missing mandatory customer field under FR-3; the Test Cases DOCX maps TC-04 to account opening under FR-4. | Follow the story's narrower Administrator-only permission and SADS's existing `PUT /customers/{id}` route shape; record undocumented behavior as implementation assumptions. The source test-document disagreement is preserved; S-13 tests use `FR3_` and `SRS55_` names. | S-13 (#50) |
| 12 | SRS Appendix C TBD-2/TBD-3; SRS §5.5; SADS API table rows 11–12; story acceptance criteria; ADR 002 | TBD-2 is resolved by retaining the seeded Savings and Current types and allowing administrators to configure them or add types. TBD-3 is resolved as a per-type daily limit. Minimum balance and daily limit are bounded at INR 10,000,000.00; interest is bounded at 20.00% p.a. A zero daily limit means no withdrawals, consistent with the existing withdrawal check. The story says Administrator-only for GET/POST/PUT, while SADS row 11 permits Officer and Admin GET; GET follows the SADS so officers can consume the list when account opening is added. Updates affect later withdrawal, transfer and interest operations, which read the current type row; transaction and audit history is not rewritten. The Test Plan PDF uses TC-05 for below-minimum account opening and TC-08 for below-minimum withdrawal; the Test Cases DOCX uses TC-04 for account opening and TC-06 for withdrawal/daily-limit rejection, so this story's tests use S14_ names where mappings diverge. ADR 002's Savings and Current example values are retained; configurable additional types, numeric ceilings and zero-limit semantics are added because that decision did not specify them. | Preserve explicit SADS read access needed by future account opening while following the story's narrower write roles.
