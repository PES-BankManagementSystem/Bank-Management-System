# Deviations log

Every place where the implementation differs from the SRS v1.0, the SADS v1.0 or the Test Plan is listed here, with the reason. The log is reviewed at the end of each sprint (S-39).

| # | Affected document and section | Deviation | Reason | Story |
|---|---|---|---|---|
| 1 | SADS 3.3 (Error Handling, concurrency conflicts) | SQLite does not have row-level locking. Balance-changing operations take a database-wide write lock (`BEGIN IMMEDIATE`) instead, so concurrent writes run one at a time. | SQLite was chosen as the relational database ([ADR 001](decisions/001-tech-stack.md)). SRS Appendix D lists record-level locking as future work, and serialised writes give the same guarantee that no update is lost. | S-01 |
| 2 | SADS 2.4 / SEC-1 (authenticated operator identity) | The S-17 deposit route records seeded Bank Officer user ID `2` as the operator because authentication and session management are not implemented yet. The operator ID is server-side and cannot be supplied by the client. | This keeps the deposit's audit and transaction records complete until S-07 provides a verified session identity. The unauthenticated demo route must not be used in a production deployment. | S-17 (#44) |
| 3 | SRS 4.2.3 (FR-3); SRS 3.4; SADS SEC-2; Test Plan TC-03/TC-04; Test Cases TC-03/TC-04 | S-11 creates a linked customer login with a generated 20-character temporary password, stores only its Argon2id hash, sets `must_change_password`, and returns the temporary password once in the 201 response for the Bank Officer to hand over. The browser keeps the bearer session in memory and shows the password only in the immediate success view. This is an explicit exception to SADS SEC-2's rule that plaintext credentials “shall never be logged, cached, or transmitted.” No email or SMS is used. This route is enabled only when the server binds to a loopback address; network deployment remains unavailable until HTTPS is implemented. | S-11's backlog acceptance requires a customer login with initial credentials but does not specify delivery. The approved implementation choice permits one-time officer handoff as a scoped exception; SRS 3.4 also says Version 1.0 requires no email or messaging interfaces. The current server has no TLS support, so one-time delivery is blocked for non-loopback listeners. SRS FR-3 §4.2.3 (page 11) specifies customer records and unique identifiers, but not login creation or credential delivery. The Test Plan (page 5) maps TC-04 to missing phone / FR-3; the separate Test Cases DOCX maps TC-04 to account opening / FR-4. S-11 follows the Test Plan's TC-04 meaning; resolve the test-document mismatch in a future documentation update. The S-11 prompt also requests email because the existing schema requires it; email is therefore accepted, validated and stored. Customer-code format (`CUS-` plus 8 random base32 characters), username = customer code, phone format, ASCII-only name characters, and DOB age limit are implementation assumptions because the source documents do not specify them. Schema version 2 adds customer codes, identification references, and the forced-change flag; `db/migrations/002_customer_credentials.sql` upgrades existing version 1 databases. A minimal in-memory bearer-session login/logout and first-login password-change endpoint were added because the existing auth routes were stubs; sessions expire after 30 minutes and are lost when the server restarts. Session enforcement is applied to S-11; other pre-existing routes are not yet wired to authentication and remain a separate security gap. |
| 4 | Issue #41 registration fields; Test Plan §14.2 TC-03; Test Cases DOCX TC-03; `db/schema.sql` | Registration requires `email`, although it is not listed among the fields in Issue #41 or the TC-03 steps. | The existing customer schema requires a unique, non-null email, so S-11 validates and stores it. | S-11 (#41) |
| 5 | Test Plan §14.2 TC-03/TC-04; Test Cases DOCX TC-03/TC-04; `tests/customer_test.cpp` | The S-11 test names do not use `TC-03` or `TC-04` identifiers. | Tests are organised by behaviour; the PR description maps them to the documented cases. | S-11 (#41) |
| 6 | SRS Appendix C TBD-5 (interest basis) | TBD-5 provisional resolution: interest uses each account's month-end UTC balance, actual days in that calendar year, and half-up rounding to paise. Completed `YYYY-MM` periods only; a zero-rounded credit is skipped. Historical opening balance is inferred from the transaction ledger because the schema has no opening-balance column. | S-22 needs a concrete reproducible calculation before the repo owner confirms the rule. See [ADR 003](decisions/003-interest-calculation-basis.md). | S-22 (#54) |
